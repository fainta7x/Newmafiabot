# Гардероб, слоты и сеты косметики — архитектурная основа

Статус: **фундамент + многослотовый контракт в PR #891**, без выпуска предметов или смены экономики. Технические слоты ниже — заготовка интерфейса, **не утверждение количества или состава сетов**.
Основной источник утверждённых квот — [COSMETICS_COMPENDIUM.md](./COSMETICS_COMPENDIUM.md).
Этот документ разделяет **уже утверждённое**, **технически подготовленное** и **открытые продуктовые решения**.

## 1. Словарь предметной области

- **Предмет (item)** — самостоятельная учётная единица каталога и постоянного инвентаря. Обладает собственными `id`, `rarity`, `slot` и версионированным графическим `asset_key`. Владение, дубликаты и возможность экипировать проверяются на уровне предмета.
- **Слот (slot)** — позиция экипировки, в которую помещается не больше одного выбранного предмета **на один ролевой образ**. Слоты определяют допустимость и порядок отрисовки слоёв, а не принадлежность к сету.
- **Сет (set)** — тематическая **коллекция нескольких самостоятельных предметов в разных слотах**, аналогично Dota 2 / World of Warcraft. У сета свой идентификатор и утверждённая редкость. Его компоненты не становятся монолитным изображением и не превращаются в один `jacketItemId`.
- **Образ (role look)** — индивидуальный набор выбранных вещей, фона и фразы для одного игрока в одной из четырёх ролей: civilian / mafia / don / sheriff. Общий инвентарь один, четыре выбора экипировки независимы.
- **Основа (portrait base)** — узнаваемое лицо/волосы/шея. Ни сет, ни вещь не подменяет эту основу.

**Принцип смешивания:** предметы разных сетов можно комбинировать по совместимым слотам. Надеть полный сет может быть удобным действием интерфейса, но отдельные вещи должны оставаться экипируемыми; массовая экипировка пока не реализована. **Бонусы за полный сет, автоматическая выдача сета, автоматическое наследование его редкости компонентами не утверждались.**

## 2. Квоты сезона и правильное количество

Владелец утвердил **5 сетов как тематических коллекций**: 2 common, 2 rare, 1 legendary. Их число нельзя отождествлять с количеством компонентов. Первоначальная матрица **34** арифметически суммирует отдельные категории товаров и *пять коллекций*; это ещё **не** утверждённое количество самостоятельных item/PNG/слоёв.

Неизвестные решения: число предметов в каждом сете; какие из отдельных 5 шляп и 6 аксессуаров входят в эти сеты; соотношение редкости каждого предмета и редкости его сета. Ничего не домножать и не автозаполнять. Отсутствие mythic в исходной матрице не даёт оснований добавлять mythic-награды.

## 3. Что уже есть в PR #891

1. `cosmetic_catalog`, `cosmetic_inventory`: каталог и владение **индивидуальными** предметами; количество, дубликаты и постоянство инвентаря. Экономику и существующие операции не меняем.
2. `player_role_looks`: четыре независимых ролевых образа. API принимает старые `hatItemId` и `jacketItemId`, а новые клиенты дополнительно передают полный `equippedItems`, фразу, фон и `expectedRevision`. Старый клиент обновляет только шляпу/пиджак; остальные слоты не теряются.
3. `cosmetic_sets`: отдельный реестр метаданных сетов (имя, редкость, сезон, признак публикации; новые записи **только draft**).
4. `cosmetic_set_items`: отношение «сет — предмет». Предмет остаётся самостоятелен в инвентаре, редкость компонентов не перезаписывается, один предмет может входить в несколько коллекций.
5. `player_role_look_equipment`: таблица `(player_id,role,slot)->item_id`, теперь **основное хранилище предметов** для всех четырёх ролей. При миграции добавляются сохранённые legacy hat/jacket; новые сохранения транзакционно заменяют набор нужной роли и обновляют старые колонки совместимости. Нельзя менять экипировку чужого игрока или использовать не принадлежащий игроку / не опубликованный / draft-ассет.

Все изменения схемы добавочные; они не генерируют предметы, не выдают их игрокам, не расходуют жетоны и не меняют Elo. Повторная инициализация схемы безопасна. Никакие существующие колонки старой схемы не удалены.

## 4. Черновой контракт сетов

Только владелец клуба, в разделе `/api/player/cosmetics/admin`:

- `GET /sets` — посмотреть определения, включая черновики, и список предметов с **их собственными** редкостями.
- `POST /sets` — создать **черновик** `{id,name,rarity,seasonId}`. Не создаёт предметов.
- `PUT /sets/:setId/items` — транзакционно заменить состав черновика объектом `{itemIds:[...]}`.

Сервер проверяет: существование сета/предметов, допустимый тип вещи для портрета, отсутствие дублей и конфликта двух компонентов в одном слоте, совместимость явно указанных сезонов. Элементы без seasonId могут использоваться в сезонном сете; этот частный допуск **не** определяет политику продаж или наград. Сет с `published=1` нельзя молча переписать. Публичного выпуска сетов, выдачи полного комплекта, массовой экипировки и применения сетовых бонусов **нет**.

Это технический интерфейс для подготовки и проверки *уже созданных черновых предметов*, а не готовый магазин. Текущие утверждённые рисунки/каталог ещё не содержат готовых элементов для новых слотов; расширение не допускает произвольные URL или слоты.

## 5. Многослотовая экипировка — технический контракт и оставшиеся решения

Новая одежда не требует дополнительных полей `shirtItemId` / `vestItemId` на каждом уровне приложения. Реализован общий контракт; ниже — какие части сделаны и что остаётся:

1. **Подготовлена техническая карта** по формату бюста 512×640 (ниже). Это не утверждённый состав будущих пяти сетов; для игровых ассетов ещё нужны проверка посадки на разных портретах и согласование с владельцем.
2. **Сделано:** `equippedItems: Partial<Record<PortraitEquipmentSlot,string>>` с разрешёнными слотами, проверкой инвентаря, готовности ассета и слота, expectedRevision и транзакционным сохранением. При отсутствии `equippedItems` запрос считается старым и меняет только hat/jacket.
3. **Сделано:** UI четырёх ролей, API и серверный snapshot работают с отдельными предметами по слотам. Новые слоты отображаются в редакторе **только когда доступны подходящие готовые предметы**; старые hat/jacket остаются. Ранее сохранённые игровые снимки читаются по старому формату.
4. **Сделано на уровне движка:** редактор и зрительский оверлей используют фиксированный порядок слоёв и сохраняют лицо отдельной основой. **Не сделано на уровне искусства:** нет подтверждённых RGBA-ассетов нового набора, посадку и потенциальные перекрытия ещё нужно проверить на реальных портретах. Ник/роль/таймер не перекрываются аватарными слоями за пределами его контейнера.
5. **Сделано:** snapshot фиксирует `portraitVersion` и массив `equippedLayers` из `slot/itemId/url` на начало игры; ключи game_key и старый snapshot-контракт сохраняются. Регистрация графических ассетов остаётся неизменяемой: обновление рисунка получает новый ключ/URL. Отдельный просмотрщик архивных снимков ещё не реализован.
6. **Проверить перед выпуском:** миграцию существующих образов, оба варианта API, приватность и владение, гонки сохранения, снятие отдельных предметов, snapshot и конфликтную логику объединения профилей. Legacy-колонки пока не удалять.

### Техническая карта слоёв бюстового портрета

Сейчас в `src/lib/roleLooks.ts` определены шесть типов — **только как расширяемые технические точки крепления**, не как шесть обязательных вещей в каждом сете:

| ID | UI-название | Порядок |
| --- | --- | --- |
| `portrait_shirt` | Рубашка / основа одежды | позади волос и лица |
| `portrait_vest` | Жилет | позади волос и лица |
| `portrait_jacket` | Верхняя одежда | позади волос и лица (совместимо с legacy) |
| `portrait_neckwear` | Галстук / шейный аксессуар | поверх основы |
| `portrait_accessory` | Украшение | поверх основы |
| `portrait_hat` | Головной убор | поверх основы (совместимо с legacy) |

Голова и волосы — фиксированная **основа**, не торговый предмет и не заменяемый слот. Эффекты `fx` не смешиваются с одеждой и в этот контракт пока не включены. Конкретные категории сетов, их количество деталей, соответствие дизайнерским частям и необходимость дополнительных слотов будут согласовываться после примерок.

**Без публикации графики:** технические идентификаторы новых слотов принимаются только при наличии выпущенного и принадлежащего игроку предмета с подходящим reviewed-ассетом. Текущие SVG остаются draft. Продуктовый выбор состава вещей владельцем ещё впереди.

## 6. Проверки перед выпуском

- Сет не имеет собственного количества в `cosmetic_inventory`; компонент можно экипировать независимо от других компонентов сета.
- Предмет принадлежит игроку, опубликован, готов, соответствует слоту; права другого игрока не подходят.
- Смена ролевого образа или сета не меняет реальные роли, ход игры, деньги, Elo и инвентарь.
- Один и тот же предмет можно использовать в разных ролевых образах без расхода экземпляров.
- При обновлении профиля и перезапуске не теряется экипировка; legacy hat/jacket продолжают работать.
- Вещи с разных слотов не закрывают лицо и важную графику. Проверять base, поштучно и в сочетаниях минимум на двух портретах.
- Награды и редактор не активируют draft-ассеты; reduced-motion учитывается для анимаций.
- Конкурирующие сохранения не затирают ревизии; снимки предыдущих игр остаются неизменными.

## 7. Граница текущего этапа

**Реализовано в коде:** таблицы сетов, компонентов и ролевой экипировки; owner-only черновой реестр сетов; универсальный серверный контракт `equippedItems`; клиентский редактор четырёх ролевых образов с самостоятельным выбором доступных вещей; упорядоченный renderer; неизменяемый snapshot всех выбранных слоёв для эфира. Legacy hat/jacket и старые снимки остаются совместимыми. Добавлены серверные и UI-тесты.

**Не реализовано и не объявляется готовым:** окончательное согласование набора одежды внутри пяти сетов; подготовленные утверждённые RGBA слои, полноценная примерка на нескольких портретах, окончательное художественное утверждение коллекций, выдача комплектов и магазинная продажа, специальные FX и экономика. Публикации/мержа/деплоя не было. Проверка CI обязательна на точном финальном коммите.


## 8. Третий этап PR #891: мастерская сетов и примерка

**Статус:** функциональность в рабочей ветке; CI и визуальные тесты подтверждаются отдельно по точному финальному коммиту. Это инженерная разработка, **не утверждение графики или ассортимента**.

### Для владельца клуба

В редакторе собственных образов «Мастерская сетов» показывается только при `canApprovePortrait` (проверяет сервер по сессии владельца). Существующие определения читаются через `GET /api/player/cosmetics/admin/sets`. Владелец выбирает каждый слот отдельной вещи, видит их наложение на уже подготовленный портрет, может сохранить или отменить изменения в составе черновика. Редкость сета и название **задаются владельцем**, а не выводятся из названий или вида предметов.

Чтобы мастерская не зависела от ручных API-запросов, добавлены защищённые `GET /api/player/cosmetics/admin/wardrobe-assets` (только безопасные зарегистрированные портретные изображения) и `GET /api/player/cosmetics/admin/wardrobe-items` (существующие предметы, включая неопубликованные). Владелец может выбрать исходный известный ассет, **сам указать название и редкость предмета** и зарегистрировать только его черновик через прежний `POST /api/player/cosmetics/admin/items` с `published=false`. Опубликованные определения сетов нельзя править через эту форму. Произвольные URL/HTML не допускаются.

Никакого автоматического выпуска, покупок, начисления опыта, выдачи инвентаря, балансовых или Elo-операций нет. Новые определения мастерской пока создаются без `seasonId`; для запуска нужен отдельный согласованный процесс привязки сезона и публикации. **Ни из сета не выводится редкость его компонентов, ни из компонентов — редкость сета.**

### Для игрока

Самостоятельный `GET /api/player/cosmetics/role-looks` теперь может содержать `sets`: только опубликованные сеты, у которых **все** составляющие опубликованы, проверены и находятся в разрешённых портретных слотах. При неготовом члене набора скрывается **весь** сет: данные неопубликованной графики не попадают в профиль.

Каждый компонент имеет самостоятельные `rarity`, `slot`, `url`, `owned`. Видно, какие вещи принадлежат игроку, какие отсутствуют; надеть отсутствующее нельзя. «Примерить весь комплект» или «Примерить доступные» изменяет **только локальный черновик выбранной роли**, без записи в БД до явного «Сохранить». Вещи из других сетов, занимающие иные слоты, не снимаются. Отдельная сворачиваемая секция сравнивает все четыре образа, не меняя реальную игровую роль и прежние игровые снимки. Старые hat/jacket API и снапшоты поддерживаются.

### Локальный прокликиваемый стенд

`e2e/cosmetics-lab.html` содержит **пять пустых безымянных рабочих ячеек**, обозначенных «Сет 1…5»; редкости соответствуют утверждённой квоте: 2 common, 2 rare, 1 legendary. Это не готовые дизайны и не записи боевого каталога. Два прежних SVG шляпы и пиджака используются **только как технические эскизы** для проверки мультислотовой примерки; мастерская показывает черновой статус рисунков. Локальные решения сохраняются в браузере под отдельным ключом и сбрасываются по кнопке. API, инвентарь и трансляции не вызываются.

### Что остаётся

Состав пяти наборов, названия, количество самостоятельных вещей, редкости их отдельных компонентов и реальная графика пока не утверждены. Значение 34 в ранней матрице включает и категории вещей, и **пять коллекций**; нельзя использовать его как финальное количество игровых itemId.

Далее: обеспечить утверждение слоёв 512×640 RGBA на нескольких узнаваемых портретах, протестировать перекрытия одежды и аксессуаров, продумать управляемую публикацию и связь черновиков с сезоном. Отдельно потребуются способы приобретения и выплаты наград, если они будут согласованы. Производственные изменения, публикация предметов и мерж/деплой не выполнялись.


## 9. Как открыть локальную мастерскую для прокликивания

В PR #891 workflow `.github/workflows/ui-preview.yml` дополнительно собирает файл `fiery-autumn-standalone.html` с помощью `scripts/buildCosmeticsLab.mjs` и кладёт его в артефакт GitHub Actions **`ui-preview-site`**.

После успешного UI preview открыть его страницу Actions → скачать `ui-preview-site` → извлечь `fiery-autumn-standalone.html` → открыть файл в обычном браузере. Это полностью автономная HTML-страница с локальным хранилищем, исходным рисунком Денди и только двумя **черновыми** отдельными слоями. Согласованные пять сетов в ней пустые; их состав можно заполнять и менять без доступа к серверу. Для сброса предусмотрена кнопка. На мобильном браузере нужно разрешить открытие локального HTML-файла.

Для разработчика эквивалентная сборка локально:

```bash
node scripts/buildCosmeticsLab.mjs temp/fiery-autumn-standalone.html
```

Не путать с реальным выпуском предметов: ни файлы из этого автономного стенда, ни его localStorage не попадают в CRM, Telegram, каталог наград или трансляцию.


## 10. Совместимость вещей между игроками — запрос владельца 14.10.2026

**Цель владельца:** одна и та же вещь используется мужчинами и девушками с разными фигурами и причёсками без индивидуальной перерисовки одежды для каждого игрока. Текущий бюстовый renderer — плоские слои 512×640; он не имеет параметрического тела, сетки деформации, заднего/переднего слоя волос или автоматически совместимых предметов. Примерка Денди проверяет один силуэт и не доказывает универсальность.

**Предлагаемая следующая основа, ещё не реализована:** отдельная узнаваемая личность (лицо, волосы) и небольшой реестр стандартных силуэтов тела в одной позе с одинаковыми опорными точками головы, шеи и плеч. Тип тела определяется геометрией фигуры, не жёстким делением по полу. Конкретное количество и параметры шаблонов ещё не согласованы.

Один itemId и одно владение сохраняются. Графика предмета получает варианты посадки по bodyTemplateId; renderer выбирает подходящий вариант. Подготавливаются варианты для типов тела, а не для каждого человека. Малые различия можно компенсировать ограниченной деформацией по точкам; сильную разницу объёма груди, плеч, воротника и складок нельзя решать произвольной растяжкой одного PNG. Отсутствующий вариант нельзя молча экипировать на несовместимое тело.

Причёска требует hairBack позади тела и hairFront поверх одежды, плюс проверенный вариант под головной убор. Это части индивидуальной основы, не отдельные покупаемые лица/волосы. Простое наложение шляпы поверх цельного слоя волос пока не решает все причёски. Базовая поза не должна ставить руки поверх меняемой одежды; если руки используются, они должны иметь отдельный совместимый слой.

Перед массовой подготовкой коллекции: проверить одну и ту же вещь на нескольких типах тела и на короткой/длинной причёске, без изменения лица; проверить снятие/замену слота, посадку воротника и шляпы, выбор соответствующего варианта и отсутствие белых краёв рубашки. Эта задача не утверждает новый ассортимент, число сетовых компонентов или bodyTemplateId API.

## 11. Каноническая проверка посадки в PR #891

`CosmeticsLab` теперь использует тот же `PlayerRoleLooksEditor`/`RolePortrait`, что личный профиль, и пять настоящих RGBA PNG в `public/character-editor/dendi-v2`: постоянные лицо/волосы/шея, рубашка, два сменных пиджака и шляпа. Это **примерка одного силуэта**, с неутверждённой графикой (`draft`), не выпущенные сезонные предметы. Квоты коллекций не изменены. Источник и преобразования экспорта записаны в manifest.json; картинки имеют общий холст 512×640.

Владелец может открыть «Примерка на Денди» внутри существующего редактора своего профиля. Она загружается только при раскрытии и использует отдельный localStorage: ни портрет владельца, ни production-инвентарь не меняются. Эквивалентный изолированный маршрут проверки — e2e/cosmetics-lab.html; автономная сборка создаётся прежним buildCosmeticsLab.mjs. Ссылка на отвергнутый векторный редактор удалена из этого пути. ## 12. Выбор технологии — обсуждение владельца 14.10.2026

Владелец спросил, есть ли более подходящий путь, чем PNG. **PNG — формат текстуры, не архитектура гардероба.** Рассмотрены: неподвижные слои, рисованная 2D-сетка с управляемой деформацией, 3D-модели тела и одежды. Предложение ассистента: проверить рисованную 2D-сетку (например PixiJS MeshGeometry) с общими опорными точками плеч/груди/талии и ограниченными, художественно проверенными профилями посадки. Передние/задние волосы и границы головы остаются отдельной задачей. Для крупных отличий фигуры возможны корректирующие формы или варианты текстур; одна автоматическая деформация не гарантирует корректные складки и свет.

Это **предложение, не утверждённый владельцем выбор и не реализованный renderer**. Не начинать массовый выпуск PNG/сетовой коллекции, не выдавать отдельную Денди-основу за универсальную систему. В текущем PR пока исправляется существующая примерка; разработка новой сетки/3D требует следующего решения владельца.

Проверенные первичные источники: https://pixijs.com/8.x/guides/components/scene-objects/mesh ; https://en.esotericsoftware.com/spine-examples-mix-and-match ; https://en.esotericsoftware.com/blog/skin-constraints-for-different-proportions ; https://threejs.org/docs/pages/SkinnedMesh.html . Эти движки дают инструменты, но не автоматически готовое искусство/посадку.
