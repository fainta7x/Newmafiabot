Реализация подготовлена одним связанным кандидатом; проверки и ограничения: [evidence](reviews/2026-10-28-publication-recovery/README.md). Исходный анализ ниже сохранён как обоснование. База: main `418628fc9b23edc1dc14c82319f04072e5757c82`, merged #1079. AR02 — имя очереди в репозитории (следующий блок после завершённого AR01). Не обещает exactly-once Telegram и не меняет адресатов, тексты, расписания, MVP или финансовые правила.

Охваченные публикации clubResult: бланки клубных/турнирных игр, итоги вечеров, входной канал, таблицы сезонов, голосование MVP, доптур, итог MVP, анонс и итог турнира. Ключи личных очередей (mvp-ask, vote-nudge, result-dm) не являются публичной отправкой: не переносить на них запрет повторов вслепую. Сверять каждый claim/finish и SQL-фильтр сканеров, включая terminal status и ожидание рассадки следующей игры. Неопределённый исход публикации не должен блокировать рассадку дольше существующих пяти минут.

Границы: weekly automation/Telegram sync outbox имеют собственные владельцы и policy; BUSINESS_RULES уже запрещает повтор неизвестного публичного исхода. Сохранить этот запрет и существующий pause, не объединять их retry-таймеры с личными уведомлениями. Это обзор смежных границ, не полный аудит Python/outbox и не разрешение переписать их.

## Единый контракт и восстановление

1. Отделить `certainty: accepted | rejected | uncertain` от признака временности отказа. Расширять общий `messageDeliveryCertainty.ts` совместимо: личные сообщения сейчас имеют другой договор повторов. Telegram: явный валидный API-отказ 429 допускает retry с Retry-After; сетевое исключение, 5xx, невалидное подтверждение — uncertain. Локальная ошибка до HTTP — точно не отправлено. VK: использовать vkDefinite, без догадок по строке ошибки.
2. Одна долговечная попытка на логическую публикацию × канал × фактический адресат/тему. Сохранять текст/вложения или воспроизводимый payload, его fingerprint, attempt ID, время, адресат, remote IDs/URL, ошибку и историю решений. Два worker/двойной клик получают только один claim. Окончание записывается условно по attempt ID: запоздалый ответ старой попытки не перетирает новую.
3. Подготовку картинки отделить от начала сетевой отправки. Подготовка безопасно повторяется. Перед HTTP сохранить sending. Каждый канал сохраняется сразу после своего ответа; сбой БД после HTTP не превращается в разрешение отправить ещё раз. Просроченное sending, где отправка могла начаться, становится uncertain. Консервативно possible loss вместо автоматического дубля; честно показать это организатору.
4. accepted → sent/published с ID; rejected временный → существующий ограниченный retry; rejected постоянный → failed; uncertain → удержание и задача организатору. Ни worker, ни API повторной публикации, ни fallback не пересылают uncertain. Новые таблицы не обязательны: общий небольшой owner попыток и адаптеры существующих таблиц предпочтительнее переноса всей истории.
5. В существующих CRM поверхностях показывать состояние каждого адресата и исходный текст. Для uncertain две явные команды: «Пост вышел» (ID/ссылка, если доступны; ручное подтверждение отмечено отдельно от API-доказательства) и «Проверил: поста нет — разрешить повтор». Вторая команда сначала записывает решение/автора/attempt ID, лишь затем допускает один новый claim; требует актуальной версии, organizer auth и двойного подтверждения риска. Подтверждение одного канала не трогает другой. Не применять автоматический поиск по сходству текста и не выдавать отсутствие ID за доказательство отсутствия поста.
6. Для фоновых итогов нужна видимая очередь удержанных публикаций в существующей CRM/задачах: одного TodayPostSheet недостаточно. Дать её GET-проекцию, действия сверки и ссылки на вечер/турнир; не создавать вторую систему личных уведомлений. Сохранять неизменный отправленный payload при частичном успехе.

## Совместимость и миграции

Аддитивные поля/таблица, сохранение прежних ключей, sent/published, remote IDs и пользовательского контента. Старые failed/retry нельзя считать доказанным отказом: часть возникла после таймаута. Не переотправлять и не переоткрывать завершённые исторические результаты; старые нетерминальные попытки с неизвестным исходом удерживать для сверки. Выбрать cutover по сохранённому состоянию, не массовому обновлению по возрасту. Проверить повторный запуск миграции и обе SQLite базы изолированно. Никаких production SQL/сообщений при разработке.

## Проверки до слияния реализации

- Timeout после удалённого принятия, HTTP 5xx, пустой/битый 2xx, неверный ID и неполный альбом: один вызов, uncertain, следующий scan/клик ничего не шлёт.
- Явный 429 с Retry-After, постоянный API-отказ, отсутствие настройки, ошибка рендера до HTTP: прежние безопасные правила, без ложного uncertain.
- Два одновременных запроса; устаревший снимок до claim; истечение lease при живом запросе; restart до/после HTTP; сбой записи результата; поздний ответ после ручного решения.
- Telegram принят/VK неизвестен и наоборот; результат одного канала сохранён при падении второго; повтор только разрешённого адресата с исходным payload.
- Photo→text fallback не запускается после uncertain. Все MVP/доптур/турнирные adapters и SQL-сканеры сохраняют certainty, terminal статусы и старые окна/расписания.
- Ручное подтверждение, разрешение повтора, stale-version/двойной клик/чужой organizer запрос; аудит решений и неизменность исторических sent/awards/голосов.
- Existing focused owners: eveningTodayPost.test.ts, clubResultPosts.test.ts, customEventPublishing.test.ts, pokerTournamentAnnouncements.integration.test.ts, messageDeliveryCertainty.test.ts; добавить маршрут/CRM и отмену. Старый тест «забрать sending после crash» сейчас требует небезопасный повтор: заменить по согласованному контракту, не ослаблять без причины.
- TypeScript/ESLint, dependency/data safety, обязательный exact-head CI. Для новых CRM состояний — четыре размера layout/text audit и один осмотр реальных снимков. Ни одного настоящего Telegram/VK POST в тестах.
