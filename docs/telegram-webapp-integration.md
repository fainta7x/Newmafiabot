# Аудит интеграции Python Telegram-бота и TypeScript Webapp

Данный документ фиксирует результаты архитектурного аудита и проектирует интеграцию существующего Python Telegram-бота с новой полнофункциональной веб-системой управления клубом спортивной мафии (Webapp).

---

## 1. Текущая архитектура систем

### 1.1. Python Telegram-бот (`aiogram` + `aiosqlite`)
* **Роль**: Основной интерфейс взаимодействия с игроками в Telegram (регистрация на вечера, просмотр личной статистики, баланс токенов, ачивки, ставки, оплата).
* **База данных**: Прямой доступ к локальной SQLite-базе `mafia_crm.db` через асинхронный драйвер `aiosqlite`.
* **Логика**: Все расчеты (Эло по формулам бота, начисление жетонов, ведение баланса долгов) выполняются непосредственно внутри Python-кода бота.

### 1.2. TS Webapp (`React` + `Express` + `SQLite/Drizzle`)
* **Роль**: Панель администратора (CRM для организаторов), пульт ведущего для ведения игр в реальном времени, турнирный модуль и публичный портал результатов.
* **База данных**: SQLite база, управляемая через Drizzle ORM.
* **Логика**: Написание игровых протоколов, расчет рейтингов для турниров, ведение CRM-задач для коммуникации с игроками.

---

## 2. Целевая архитектура (API-First)

Для обеспечения надежности, масштабируемости и предотвращения конфликтов параллельной записи в БД утверждается переход на **API-First архитектуру**:

1. **Единый владелец данных**: Express-бэкенд является единственным владельцем базы данных SQLite и бизнес-логики. Прямой доступ Python-бота к файлу базы данных полностью исключается.
2. **REST API**: Python-бот взаимодействует с системой исключительно как клиент бэкенда через внутренний REST API (по адресу `127.0.0.1` или защищенному каналу).
3. **Сервисная авторизация**: Все запросы бота к API бэкенда авторизуются с использованием статического токена безопасности (`BOT_API_SECRET`), передаваемого в HTTP-заголовках (например, `X-Bot-Token`).
4. **Разделение ответственности**: Бот отвечает только за UI/UX в Telegram, обработку пользовательского ввода и отображение данных. Бэкенд отвечает за валидацию, транзакции, изменение балансов, пересчет Эло и обновление статусов.

## 3. Сопоставление сущностей и таблиц (Mapping)

При переходе на единую базу данных сущности старой БД бота мапируются на таблицы новой схемы Webapp следующим образом:

| Таблица в боте (Python) | Таблица/Сущность в Webapp (TS) | Описание соответствия и правила переноса |
| :--- | :--- | :--- |
| `users` | `players` | Игроки клуба. Числовой `users.user_id` (Telegram ID) сохраняется в текстовое поле `players.telegram_user_id`. `players.id` генерируется как UUID. |
| `evening_booking` | `evening_participants` | Текущая запись на ближайший вечер. Статус записи и время прибытия раскладываются на соответствующие поля. |
| `evening_history` | `evening_participants` + `game_evenings` | Исторические записи посещений вечеров. Переносятся как связи участника с завершенными игровыми вечерами. |
| `game_history` | `games` | Завершенные обычные (не турнирные) игры. Поля протокола переводятся в JSON/структурированный вид. |
| `game_slots_history` | `games.slots_json` (или будущая детальная таблица) | Индивидуальные результаты игроков в конкретных играх. На данный момент в Webapp обычные игры хранятся преимущественно в виде JSON-массива в `games.slots_json`. |
| `transactions` | `financial_transactions` | Финансовые транзакции (оплаты, долги). Сумма долга приводится к единому формату. |
| `user_achievements` | *Отсутствует* | Достижения игроков. Требуется создание новой таблицы `player_achievements` в схеме Webapp. |
| `user_bets` / `bets_active` | *Отсутствует* | Активные и завершенные ставки на игры. Требуется перенос логики ставок в бэкенд и создание таблиц ставок. |
| `elo_ratings` | `players.elo` | Рейтинги Эло. Требуется синхронизация масштабов и стартовых значений рейтинга. |

## 4. Функциональное покрытие и дефицит схемы

### 4.1. Функции бота, поддерживаемые в новой схеме Webapp
* **Профиль игрока**: Поля `nickname`, `full_name`, `telegram_username`, `phone`, `elo`, `tokens` полностью поддерживаются в таблице `players`.
* **Игровые вечера**: Таблица `game_evenings` полностью покрывает логику дат проведения, локаций и настроек вечеров.
* **Запись на вечер**: Связующая таблица `evening_participants` детально описывает состояние записи игрока (регистрация, посещение, статус оплаты).
* **Финансовый учет**: Таблица `financial_transactions` покрывает логику начисления оплат и расходов.

### 4.2. Дефицит схемы (функции бота без поддержки в Webapp)
* **Ачивки (Достижения)**: Таблица `user_achievements` старого бота не имеет аналога в схеме Webapp.
* **Игровые ставки**: Таблицы `bets_active` и `user_bets` полностью отсутствуют в схеме Drizzle.
* **Магазин за жетоны**: Логика товаров и покупок за жетоны отсутствует в бэкенде.
* **Детальная история слотов обычных игр**: В отличие от турнирного модуля, где результаты детализированы до уровня `tournament_game_player_results`, обычные игры в таблице `games` хранят протокол в текстовом виде и JSON-строке, что затрудняет аналитические SQL-запросы без парсинга JSON.

## 5. Критические несовместимости

В процессе аудита выявлен ряд фундаментальных несовместимостей, которые делают невозможным простое подключение бота и бэкенда к одной базе данных без предварительного рефакторинга:

1. **Идентификация пользователя (`user_id` vs `id`)**:
   * *Бот*: Использует числовой Telegram ID (`user_id` типа `INTEGER`) в качестве первичного ключа игрока.
   * *Webapp*: Использует случайно генерируемый `UUID` (`id` типа `TEXT`) как первичный ключ. Связь с Telegram выполняется через уникальное индексированное поле `telegram_user_id` (`TEXT`).
   * *Решение*: Бот должен запрашивать игрока по Telegram ID, получать UUID из бэкенда и использовать именно UUID для всех последующих транзакционных действий (запись на вечер, оплата).

2. **Масштаб и формулы Эло (1500 vs 1000)**:
   * *Бот*: Стартовое Эло равно `1500`. Используется кастомная формула расчета изменений в зависимости от ролей и исходов.
   * *Webapp*: Стартовое Эло равно `1000`. Логика расчета Эло в live-движке отличается.
   * *Решение*: Логика Эло должна быть полностью перенесена на сторону Express-бэкенда. Требуется принять единый стандарт стартового Эло (рекомендуется `1000`) и единую формулу начисления. При миграции старые рейтинги должны быть пересчитаны или импортированы со смещением.

3. **Масштаб жетонов (Tokens)**:
   * *Бот*: Жетоны начисляются сотнями и тысячами за различные активности.
   * *Webapp*: Жетоны (поле `tokens` в `players`) начисляются единицами (по 1–2 жетона).
   * *Решение*: Выравнивание масштаба жетонов. Вся логика инкремента/декремента токенов должна выполняться на бэкенде.

4. **Формат ведения долгов**:
   * *Бот*: Отрицательный баланс в поле `debt` означает задолженность игрока перед клубом (например, `-400`).
   * *Webapp*: Долг рассчитывается как строго положительная величина на основе разницы полей участия: `amount_due - amount_paid` (где `amount_due > amount_paid`).
   * *Решение*: При миграции и интеграции бот должен запрашивать баланс через API, а бэкенд будет отдавать вычисленное значение задолженности в понятном боту формате.

5. **Статусы записи на вечер**:
   * *Бот*: Статусы записи хранятся в виде строк: `Вовремя`, `Позже`, `Не идёт`.
   * *Webapp*: Статус разделен на два измерения: `registration_status` (`invited`, `registered`, `confirmed`, `waitlist`, `cancelled`) и `arrival_status` (`unknown`, `on_time`, `late`).
   * *Решение*: Мапинг статусов при интеграции:
     * `Вовремя` -> `registration_status='confirmed'`, `arrival_status='on_time'`
     * `Позже` -> `registration_status='confirmed'`, `arrival_status='late'`
     * `Не идёт` -> `registration_status='cancelled'`

6. **Форматы дат**:
   * *Бот*: Старые даты в БД бота часто хранятся в текстовом формате `ДД.ММ` или `ДД.ММ.ГГГГ` без указания года или таймзоны.
   * *Webapp*: Все временные метки хранятся строго в стандарте ISO 8601 (строки UTC или с явным смещением, например `YYYY-MM-DDTHH:mm:ss.sssZ`).
   * *Решение*: Валидация и нормализация дат на стороне бэкенда при импорте.

7. **Непересекающиеся скрипты миграции**:
   * Скрипт `migrateLegacyData.ts` импортирует статические данные из JSON-файла `mafia_db.json`, но он не умеет работать с «живой» SQLite-базой Python-бота. Подключение бота напрямую к новой базе на данном этапе полностью сломает логику его работы из-за различий в схеме.

8. **Конфликт путей к БД**:
   * В конфигурациях проекта присутствуют разные имена файлов баз данных: `mafia_crm.db`, `mafia_crm.sqlite` и `mafia_club.db`. Настоящим аудитом фиксируется необходимость унификации имени БД до `mafia_crm.sqlite` на последующих этапах рефакторинга.

## 6. Проектируемая карта API (REST Contract)

Для взаимодействия бота с бэкендом предлагается следующий набор эндпоинтов. Все эндпоинты требуют заголовка авторизации бота: `X-Bot-Token: <SECRET>`.

### 6.1. Сервисные методы
* **GET `/api/bot/health`**
  * *Назначение*: Проверка доступности бэкенда и валидности токена бота.
  * *Вход*: Нет.
  * *Выход*: `{"status": "ok", "version": "1.0.0"}`.
  * *Идемпотентность*: Да.
  * *Доступ*: Только Python-бот.

### 6.2. Управление игроками
* **GET `/api/bot/players/by-telegram/:tg_id`**
  * *Назначение*: Поиск игрока по Telegram ID.
  * *Выход*: Данные игрока (`id` (UUID), `nickname`, `elo`, `tokens`, `outstanding_debt`) или `404 Not Found`.
  * *Идемпотентность*: Да.

* **POST `/api/bot/players`**
  * *Назначение*: Регистрация нового игрока через бота.
  * *Вход*: `{"telegram_user_id": "123456", "nickname": "Neo", "full_name": "John Doe", "telegram_username": "neo_tg"}`
  * *Выход*: Созданный объект игрока с UUID.
  * *Идемпотентность*: Нет.

### 6.3. Запись на вечера
* **GET `/api/bot/evenings/active`**
  * *Назначение*: Получение ближайшего опубликованного или активного игрового вечера для записи.
  * *Выход*: Объект вечера (`id`, `title`, `starts_at`, `venue`, `status`, `capacity`, `registered_count`).
  * *Идемпотентность*: Да.

* **POST `/api/bot/evenings/:evening_id/book`**
  * *Назначение*: Запись игрока на вечер или обновление статуса его записи.
  * *Вход*: `{"player_id": "<UUID>", "status": "Вовремя" | "Позже" | "Не идёт"}`
  * *Выход*: Объект `evening_participants`.
  * *Идемпотентность*: Да.

* **GET `/api/bot/evenings/:evening_id/participants`**
  * *Назначение*: Список записавшихся участников вечера.
  * *Выход*: Массив участников с их никнеймами и статусами прибытия.
  * *Идемпотентность*: Да.

### 6.4. Финансы и Оплаты
* **POST `/api/bot/payments/request`**
  * *Назначение*: Регистрация намерения оплаты за вечер (игрок прислал чек).
  * *Вход*: `{"player_id": "<UUID>", "evening_id": "<UUID>", "amount": 400, "transaction_details": "string"}`
  * *Выход*: Созданная транзакция со статусом ожидания проверки администратором.
  * *Идемпотентность*: Нет.

### 6.5. Статистика и Рейтинги
* **GET `/api/bot/players/:player_id/stats`**
  * *Назначение*: Получение расширенной игровой статистики (сыграно игр, побед за разные роли, средние доп. баллы).
  * *Выход*: Объект статистики (рассчитывается на бэкенде динамически из истории игр).
  * *Идемпотентность*: Да.

## 7. Поэтапный план миграции и интеграции

Переход на целевую архитектуру должен выполняться строго поэтапно с сохранением работоспособности системы на каждом шаге.

```
+-------------------------------------------------------+
| Этап 1: Сервисная авторизация и Health-Check          |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
| Этап 2: Идентификация игрока и профиль                |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
| Этап 3: Игровые вечера и запись                       |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
| Этап 4: Оплаты и финансовые транзакции                |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
| Этап 5: Единая логика обычных игр, Эло и жетонов       |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
| Этап 6: Статистика, ачивки, магазин и ставки          |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
| Этап 7: Безопасный импорт старой SQLite-базы в новую  |
+---------------------------+---------------------------+
                            |
                            v
+-------------------------------------------------------+
| Этап 8: Отключение прямой работы бота со старой БД    |
+-------------------------------------------------------+
```

### Этап 1: Сервисная авторизация и Health-Check
* **Действие**: Реализовать в Express-бэкенде обработку заголовка `X-Bot-Token` и один тестовый эндпоинт `/api/bot/health`. В Python-боте написать клиентский модуль для выполнения HTTP-запросов к бэкенду.
* **Условие готовности**: Бот успешно пингует бэкенд при запуске.
* **Безопасный откат**: Отключение HTTP-клиента в боте, возврат к полностью автономной работе.

### Этап 2: Идентификация игрока и профиль
* **Действие**: Реализовать эндпоинты поиска по Telegram ID и создания игрока. Бот при командах `/start` и `/profile` сначала ищет игрока через API бэкенда. Если игрок не найден в новой базе, бот временно ищет его в локальной старой БД.
* **Условие готовности**: Синхронный поиск игроков работает в гибридном режиме.
* **Безопасный откат**: Возврат бота к чтению профиля исключительно из локальной БД.

### Этап 3: Игровые вечера и запись
* **Действие**: Реализовать на бэкенде API получения активного вечера и записи на него. Бот переводится на отправку запросов записи через REST API.
* **Условие готовности**: Записи пользователей через бота мгновенно отображаются в CRM-панели организатора на Webapp.
* **Безопасный откат**: Откат к записи через локальную таблицу `evening_booking`.

### Этап 4: Оплаты и финансовые транзакции
* **Действие**: Интеграция платежных уведомлений. Запросы на оплату регистрируются бэкендом как транзакции со статусом ожидания подтверждения. Подтверждение оплаты организатором в CRM веб-интерфейса отправляет вебхук или уведомление боту для пересылки пользователю.
* **Условие готовности**: Оплаты подтверждаются в веб-панели и баланс игрока обновляется.
* **Безопасный откат**: Ручное ведение балансов долгов в боте.

### Этап 5: Единая логика обычных игр, Эло и жетонов
* **Действие**: Перенос алгоритма расчета рейтинга Эло и жетонов на бэкенд. Ведущий сохраняет игры через пульт веб-интерфейса, бэкенд производит транзакционное обновление рейтингов всех 10 участников.
* **Условие готовности**: Корректный автоматический пересчет рейтинга Эло в общей базе при сохранении игр.
* **Безопасный откат**: Использование ручных корректировок рейтингов.

### Этап 6: Статистика, ачивки, магазин и ставки
* **Действие**: Расширение схемы Drizzle для поддержки достижений (`player_achievements`) и ставок. Реализация соответствующих API-методов. Перенос игровой логики ставок из Python-кода бота на бэкенд.
* **Условие готовности**: Полный отказ бота от самостоятельных расчетов игровых показателей.
* **Безопасный откат**: Выключение разделов ставок и достижений в боте.

### Этап 7: Безопасный импорт старой SQLite-базы в новую
* **Действие**: Написание полноценного скрипта однократного импорта реальной SQLite-базы бота `mafia_crm.db` в новую базу `mafia_crm.sqlite` с конвертацией типов данных (Telegram ID в UUID, нормализация статусов прибытия, конвертация исторических дат в ISO).
* **Условие готовности**: Успешное выполнение скрипта без ошибок уникальности и внешних ключей.
* **Безопасный откат**: Восстановление структуры новой БД из бэкапа, повторный запуск импорта с исправленными правилами мапинга.

### Этап 8: Отключение прямой работы бота со старой БД
* **Действие**: Полное удаление локальной базы данных бота `mafia_crm.db` и кода инициализации таблиц `init_db()` в Python. Переключение бота исключительно на работу по REST API. Унификация путей баз данных.
* **Условие готовности**: Бот успешно функционирует без локального файла БД. Старая БД безопасно архивируется.

## 8. Выводы и рекомендации аудита

1. **Запрет прямой интеграции на уровне БД**: Подключение Python-бота и Express-приложения к одному файлу базы данных SQLite на текущем этапе строго запрещено. Различия в схемах (UUID против Telegram ID, разные подходы к расчету Эло и хранению долгов) приведут к взаимной порче данных.
2. **Перенос бизнес-логики**: Расчет Эло, балансов долгов и жетонов должен быть изъят из кода бота и сосредоточен в контроллерах бэкенда. Бот должен стать «тонким клиентом».
3. **Унификация файлов баз данных**: После завершения интеграции и полной миграции данных имя файла рабочей базы данных должно быть зафиксировано как `mafia_crm.sqlite`, а дублирующие конфигурационные файлы и переменные (`mafia_crm.db`, `mafia_club.db`) удалены.
4. **Резервное копирование**: На протяжении всех этапов миграции необходимо сохранять автоматическое резервное копирование исходной базы данных бота.
