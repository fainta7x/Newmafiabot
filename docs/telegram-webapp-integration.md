# Аудит интеграции Python Telegram-бота и TypeScript Webapp

Данный документ фиксирует результаты архитектурного аудита и проектирует интеграцию существующего Python Telegram-бота с новой полнофункциональной веб-системой управления клубом спортивной мафии (Webapp).

---

## 1. Текущая архитектура систем

### 1.1. Python Telegram-бот (`aiogram` + `aiosqlite`)
* **Роль**: Основной интерфейс взаимодействия с игроками в Telegram (регистрация на вечера, просмотр личной статистики, баланс токенов, ачивки, ставки, оплата).
* **База данных**: Прямой доступ к локальной SQLite-базе `mafia_crm.db` через асинхронный драйвер `aiosqlite`.
* **Логика**: Все расчеты (Эло по формулам бота, начисление жетонов, ведение баланса долгов) выполняются непосредственно внутри Python-кода бота.

### 1.2. TS Webapp (`React` + `Express` + `SQLite/Drizzle`)
* **Роль**: Панель администратора (CRM для организаторов), пульт ведущего для ведения игр в реальном времени, турнирный модуль и публичный портал результатов.
* **База данных**: SQLite база, управляемая через Drizzle ORM.
* **Логика**: Написание игровых протоколов, расчет рейтингов для турниров, ведение CRM-задач для коммуникации с игроками.

---

## 2. Целевая архитектура (API-First)

Для обеспечения надежности, масштабируемости и предотвращения конфликтов параллельной записи в БД утверждается переход на **API-First архитектуру**:

1. **Единый владелец данных**: Express-бэкенд является единственным владельцем базы данных SQLite и бизнес-логики. Прямой доступ Python-бота к файлу базы данных полностью исключается.
2. **REST API**: Python-бот взаимодействует с системой исключительно как клиент бэкенда через внутренний REST API (по адресу `127.0.0.1` или защищенному каналу).
3. **Сервисная авторизация**: Все сервисные запросы бота к API бэкенда авторизуются с использованием статического токена безопасности (`BOT_API_SECRET`), передаваемого в HTTP-заголовках (`X-Bot-Token`). Действия организатора остаются под классической JWT-авторизацией организатора.
4. **Разделение ответственности**: Бот отвечает только за UI/UX в Telegram, обработку пользовательского ввода и отображение данных. Бэкенд отвечает за валидацию, транзакции, изменение балансов, пересчет Эло и обновление статусов.

## 4. Правила ведения и расчета статистики

Для исключения рассинхронизации данных между ботом и веб-интерфейсом утверждаются следующие правила:

1. **Запрет независимых счетчиков**: Статистические показатели игроков (такие как `games_played`, `games_won`, победы за мафию/мирных, количество фолов, сумма дополнительных баллов) **не должны** храниться в виде дублирующихся независимых счетчиков, которые инкрементируются ботом и веб-панелью отдельно.
2. **Расчет из единого источника**: Вся игровая статистика должна динамически рассчитываться бэкендом на основе единой сохраненной истории игровых результатов (таблицы `games` для обычных игр и `tournament_game_player_results` для турниров).
3. **Единые транзакции состояния**: Поля текущего состояния `players.elo` (рейтинг Эло) и `players.tokens` (баланс жетонов) могут хранить денатурализованные значения для быстрого доступа, однако любые изменения этих полей должны производиться строго в рамках единой транзакции бэкенда и обязательно сопровождаться записью в историю операций/транзакций.
4. **Разделение типов игр**: Турнирные игры и обычные игровые вечера должны иметь строго разделенные источники статистики либо явный признак типа соревнования (`competition_type`), чтобы результаты фановых обычных игр случайно не влияли на официальный турнирный зачет, и наоборот.

## 5. Критические несовместимости

В процессе аудита выявлен ряд фундаментальных несовместимостей, которые делают невозможным простое подключение бота и бэкенда к одной базе данных без предварительного рефакторинга:

1. **Идентификация пользователя (`user_id` vs `id`)**:
   * *Бот*: Использует числовой Telegram ID (`user_id` типа `INTEGER`) в качестве первичного ключа игрока.
   * *Webapp*: Использует случайно генерируемый `UUID` (`id` типа `TEXT`) как первичный ключ. Связь с Telegram выполняется через уникальное индексированное поле `telegram_user_id` (`TEXT`).
   * *Связь*: Выполняется строго по уникальному полю `players.telegram_user_id`. Бот на первом шаге находит игрока по Telegram ID, получает его UUID и в дальнейшем оперирует исключительно UUID.

2. **Масштаб и формулы Эло (1500 vs 1000)**:
   * *Бот*: Стартовое Эло равно `1500`. Используется кастомная формула расчета изменений в зависимости от ролей и исходов.
   * *Webapp*: Стартовое Эло в CRM и турнирах по умолчанию равно `1000`. Логика пересчета отличается.
   * *Решение*: **Единая формула и стартовое значение рейтинга еще должны быть выбраны отдельно.** До принятия окончательного решения исторические значения Эло изменять нельзя. Наиболее безопасный вариант миграции — первоначально сохранить текущие рейтинги игроков без пересчета. Перед переносом расчетов рейтинга на бэкенд необходимо провести эталонные тестовые партии, сравнивающие результаты старого Python-алгоритма и нового backend-алгоритма, чтобы гарантировать полную идентичность результатов.

3. **Масштаб жетонов (Tokens)**:
   * *Бот*: Жетоны начисляются сотнями и тысячами за различные активности.
   * *Webapp*: Жетоны (поле `tokens` в `players`) начисляются единицами (по 1–2 жетона).
   * *Решение*: Бот и webapp сейчас по-разному изменяют жетоны, поэтому подключать их к общей записи до создания единой серверной логики начисления нельзя. Все изменения баланса токенов должны проходить через бэкенд-транзакции.

4. **Формат ведения долгов**:
   * *Бот*: Отрицательный баланс в поле `debt` означает задолженность игрока перед клубом (например, `-400`).
   * *Webapp*: Долг рассчитывается как строго положительная величина на основе разницы полей участия: `amount_due - amount_paid`.
   * *Решение*: При миграции старый долг конвертируется в положительную разницу. Бот запрашивает баланс через API, бэкенд отдает вычисленное значение задолженности в понятном боту формате.

5. **Статусы записи на вечер**:
   * *Бот*: Статусы записи хранятся в виде строк: `Вовремя`, `Позже`, `Не идёт`.
   * *Webapp*: Статус разделен на два измерения: `registration_status` (`invited`, `registered`, `confirmed`, `waitlist`, `cancelled`) и `arrival_status` (`unknown`, `on_time`, `late`).
   * *Решение*: API не должно принимать пользовательские строки `Вовремя`, `Позже`, `Не идёт` как внутренний формат. Бот должен самостоятельно переводить их в канонические поля перед отправкой запроса бэкенду.

6. **Форматы дат**:
   * *Бот*: Старые даты в БД бота часто хранятся в текстовом формате `ДД.ММ` или `ДД.ММ.ГГГГ`.
   * *Webapp*: Все временные метки хранятся строго в стандарте ISO 8601 (UTC).

7. **Непересекающиеся скрипты миграции**:
   * Скрипт `migrateLegacyData.ts` импортирует статические данные из JSON-файла `mafia_db.json`, но он не умеет работать с «живой» SQLite-базой Python-бота. Подключение бота напрямую к новой базе на данном этапе полностью сломает логику его работы из-за различий в схеме.

8. **Конфликт путей к БД**:
   * Пути `mafia_crm.db`, `mafia_crm.sqlite` и значение `DATABASE_PATH` пока расходятся в различных конфигурациях и должны быть исправлены на последующих этапах.

## 6. Проектируемая карта API (REST Contract)

Для взаимодействия бота с бэкендом предлагается следующий набор эндпоинтов.

> 🔒 **Правило авторизации**:
> * Все **bot-only эндпоинты** (`/api/bot/*`) защищаются токеном `BOT_API_SECRET` через заголовок `X-Bot-Token`.
> * Все **организаторские/администраторские действия** (такие как верификация платежей, создание объявлений) выполняются строго под классической организаторской JWT-авторизацией и **не должны** ошибочно размещаться как bot-only эндпоинты.

### 6.1. Сервисные методы и здоровье
* **GET `/api/bot/health`**
  * *Назначение*: Проверка доступности бэкенда и валидности токена бота.
  * *Вход*: Нет.
  * *Выход*: `{"status": "ok", "service": "mafia-webapp", "api_version": "1"}`.
  * *Идемпотентность*: Да.
  * *Права доступа*: Только Python-бот (по `BOT_API_SECRET`).

### 6.2. Управление игроками и профиль
* **PUT `/api/bot/players/by-telegram/:tg_id`**
  * *Назначение*: Идемпотентная синхронизация или создание игрока по Telegram ID. Предотвращает дубликаты при повторном вызове команды `/start`.
  * *Вход*: `{"nickname": "Neo", "full_name": "John Doe", "telegram_username": "neo_tg"}` (поля `phone` в `users` нет!)
  * *Выход*: `{"id": "<UUID>", "telegram_user_id": "123456", "nickname": "Neo", "status": "synced"}`
  * *Идемпотентность*: Да.
  * *Права доступа*: Только Python-бот.

* **GET `/api/bot/players/by-telegram/:tg_id/profile`**
  * *Назначение*: Получение полного профиля игрока для отображения по команде `/profile`.
  * *Вход*: Нет.
  * *Выход*: `{"id": "<UUID>", "nickname": "Neo", "elo": 1500, "tokens": 120, "outstanding_debt": 400, "registered_at": "ISO-Date"}`
  * *Идемпотентность*: Да.
  * *Права доступа*: Только Python-бот.

### 6.3. Игровые вечера и запись
* **GET `/api/bot/evenings/nearest`**
  * *Назначение*: Получение ближайшего опубликованного или активного игрового вечера для записи.
  * *Вход*: Нет.
  * *Выход*: `{"id": "<UUID>", "title": "Пятничный вечер", "starts_at": "ISO-Date", "venue": "Клуб Мафия", "capacity": 10, "registered_count": 4}`
  * *Идемпотентность*: Да.
  * *Права доступа*: Только Python-бот.

* **POST `/api/bot/evenings/:evening_id/book`**
  * *Назначение*: Запись игрока на вечер, изменение или отмена записи.
  * *Вход*: `{"player_id": "<UUID>", "registration_status": "registered" | "cancelled", "arrival_status": "on_time" | "late" | "unknown"}`
  * *Выход*: `{"id": "<UUID>", "player_id": "<UUID>", "evening_id": "<UUID>", "registration_status": "registered", "arrival_status": "on_time"}`
  * *Идемпотентность*: Да (при повторе тех же статусов).
  * *Права доступа*: Только Python-бот.

* **GET `/api/bot/evenings/:evening_id/participants`**
  * *Назначение*: Получение списка участников, записанных на вечер.
  * *Вход*: Нет.
  * *Выход*: `[{"player_id": "<UUID>", "nickname": "Neo", "arrival_status": "on_time"}]`
  * *Идемпотентность*: Да.
  * *Права доступа*: Только Python-бот.

### 6.4. Задолженность и Оплаты
* **GET `/api/bot/players/:player_id/debt`**
  * *Назначение*: Получение текущей задолженности игрока перед клубом.
  * *Вход*: Нет.
  * *Выход*: `{"player_id": "<UUID>", "outstanding_debt": 400}`
  * *Идемпотентность*: Да.
  * *Права доступа*: Только Python-бот.

* **POST `/api/bot/payments/request`**
  * *Назначение*: Создание запроса на подтверждение оплаты (игрок отправил чек в боте).
  * *Вход*: `{"player_id": "<UUID>", "evening_id": "<UUID>", "amount": 400, "receipt_image_url": "string"}`
  * *Выход*: `{"payment_request_id": "<UUID>", "status": "pending_confirmation", "amount": 400}`
  * *Идемпотентность*: Нет.
  * *Права доступа*: Только Python-бот.

* **POST `/api/organizer/payments/:request_id/verify`** *(Организаторский эндпоинт, НЕ bot-only!)*
  * *Назначение*: Подтверждение или отклонение запроса на оплату организатором в CRM.
  * *Вход*: `{"status": "approved" | "rejected", "comment": "Оплата получена"}`
  * *Выход*: `{"payment_request_id": "<UUID>", "status": "approved", "transaction_id": "<UUID>"}`
  * *Идемпотентность*: Да.
  * *Права доступа*: Организатор (через Web CRM по JWT-сессии).

### 6.5. Игровая история, Статистика и Достижения
* **GET `/api/bot/players/:player_id/games`**
  * *Назначение*: Получение истории игр пользователя.

## 7. Поэтапный план миграции и интеграции

Переход на целевую архитектуру должен выполняться строго поэтапно. Для исключения рисков рассинхронизации данных, **переключение функций бота на работу через API бэкенда происходит последовательно, строго по одной изолированной области (домену)**.

---

### Этап 1: Сервисная авторизация и Health-Check
* **Действие**: Реализовать в Express-бэкенде обработку заголовка `X-Bot-Token` и тестовый эндпоинт `/api/bot/health`. В Python-боте написать клиентский модуль для выполнения HTTP-запросов к бэкенду.
* **Условие готовности**: Бот успешно пингует бэкенд при запуске.
* **Безопасный откат**: Полное отключение HTTP-клиента в Python-боте, возврат к полностью автономной работе бота. Исключен риск dual-write, так как запись в бэкенд на этом этапе не производится.

---

### Этап 2: Идентификация игрока и профиль (Домен "Профиль")
* **Действие**: Реализовать эндпоинты PUT `/api/bot/players/by-telegram/:tg_id` (идемпотентная синхронизация) и GET для получения профиля. Бот при командах `/start` и `/profile` обращается к API. 
* **Переходный режим**: Допускается только временное чтение старой БД как fallback, если игрока еще нет в новой системе.
  * ❌ **Запрещено**: Параллельная запись одного действия в две базы данных.
  * ❌ **Запрещено**: Независимое изменение профиля одновременно в боте и webapp.
  * ❌ **Запрещено**: Автоматическое копирование данных без проверки конфликтов.
  * После чтения старого профиля его перенос в новую систему должен выполняться через идемпотентный бэкенд-API.
* **Условие готовности**: Бот успешно считывает профили синхронизированных игроков из новой базы.
* **Безопасный откат**: Отключение API-запросов профилей в боте, возврат к чтению/записи профиля только в локальной БД бота.

---

### Этап 3: Игровые вечера и запись (Домен "Запись")
* **Действие**: Реализовать на бэкенде API получения активного вечера и записи на него. Бот переводится на отправку запросов записи через REST API.
* **Условие готовности**: Записи пользователей через бота мгновенно отображаются в CRM-панели организатора на Webapp.
* **Безопасный откат**: 
  1. **Остановить запись и активность в боте / CRM**.
  2. Сверить и выгрузить все изменения, сделанные через API за время тестирования.
  3. Перенести эти записи разовым безопасным скриптом в локальную таблицу `evening_booking` бота.
  4. Только после полной сверки переключить бота обратно на локальную таблицу `evening_booking`. 
  * ❌ **Запрещено**: Слепо включать устаревшие локальные таблицы без контролируемого согласования данных!

---

### Этап 4: Оплаты и финансовые транзакции (Домен "Оплаты")
* **Действие**: Реализация эндпоинтов запросов на оплату и подтверждений. Оплаты подтверждаются организатором в CRM-панели Webapp, баланс игрока обновляется на бэкенде.
* **Условие готовности**: Оплаты подтверждаются в веб-панели, задолженность игрока корректно пересчитывается.
* **Безопасный откат**: 
  1. **Приостановить проведение финансовых операций** в боте и CRM.
  2. Провести полный аудит и сверку всех транзакций, проведённых через API.
  3. Перенести новые подтверждённые транзакции в локальную таблицу `transactions` бота и скорректировать баланс `debt` в `users`.
  4. Переключить финансовые модули бота обратно на локальные таблицы.

---

### Этап 5: Единая логика обычных игр, Эло и жетонов (Домен "Игры и Рейтинг")
* **Действие**: Перенос алгоритма расчета рейтинга Эло и жетонов на бэкенд. Ведущий сохраняет игры через пульт веб-интерфейса, бэкенд производит транзакционное обновление рейтингов.
* **Условие готовности**: Корректный автоматический пересчет рейтинга Эло в общей базе при сохранении обычных игр. Проверено совпадение результатов со старым Python-алгоритмом на тестовом наборе игр.
* **Безопасный откат**: 
  1. **Остановить сохранение новых игр на пульте ведущего**.
  2. Сверить все сыгранные за тестовый период игры в таблицах `games` и `game_slots_history`.
  3. Перенести протоколы сыгранных игр в локальные таблицы бота `game_history` и `game_slots_history` и пересчитать Эло локальным Python-алгоритмом.
  4. Вернуть расчет рейтинга обратно на сторону бота, временно заблокировав сохранение через пульт веб-интерфейса.

* **Безопасный откат**: 
  1. **Приостановить ставки, достижения и покупки в магазине в боте**.
  2. Сверить все новые ставки, покупки и выданные достижения, зафиксированные на бэкенде.
  3. Безопасно перенести новые записи в локальные таблицы бота `user_bets`, `bets_active`, `user_achievements` и баланс `tokens` в `users`.
  4. Переключить соответствующие модули бота обратно на локальную работу.

### Этап 7: Безопасный импорт старой SQLite-базы в новую
* **Действие**: Написание полноценного скрипта однократного импорта реальной SQLite-базы бота `mafia_crm.db` в новую базу `mafia_crm.sqlite` с конвертацией типов данных (Telegram ID в UUID, нормализация статусов прибытия, конвертация исторических дат в ISO).
* **Условие готовности**: Успешное выполнение скрипта без ошибок уникальности и внешних ключей.
* **Безопасный откат**: Восстановление структуры новой БД из бэкапа, повторный запуск импорта с исправленными правилами мапинга.

---

### Этап 8: Отключение прямой работы бота со старой БД
* **Действие**: Полный перевод бота на REST API бэкенда и прекращение использования локальной базы данных.
* **Последовательность отключения**:
  1. Полностью остановить запись и активность в старом боте.
  2. Создать проверенный бэкап старой БД `mafia_crm.db`.
  3. Выполнить финальный импорт данных.

  7. Зафиксировать контрольную сумму (SHA-256) и точную дату архивирования в логах.

* **Условие готовности**: Бот и веб-интерфейс успешно функционируют на единой базе данных бэкенда, старая база находится в архивном состоянии.

## 8. Выводы и рекомендации аудита

1. **Запрет прямой интеграции на уровне БД**: Подключение Python-бота и Express-приложения к одному файлу базы данных SQLite на текущем этапе строго запрещено. Различия в схемах (UUID против Telegram ID, разные подходы к расчету Эло и хранению долгов) приведут к взаимной порче данных.
2. **Перенос бизнес-логики**: Расчет Эло, балансов долгов и жетонов должен быть изъят из кода бота и сосредоточен в контроллерах бэкенда. Бот должен стать «тонким клиентом».
3. **Унификация файлов баз данных**: После завершения интеграции и полной миграции данных имя файла рабочей базы данных должно быть зафиксировано как `mafia_crm.sqlite`, а дублирующие конфигурационные файлы и переменные (`mafia_crm.db`, `mafia_club.db`) удалены.
4. **Резервное копирование**: На протяжении всех этапов миграции необходимо сохранять автоматическое резервное копирование исходной базы данных бота.
